# 待研究的问题，以及业界已经怎么解了

上一版这份文档只列了「我们做不到什么」，没回答「别人怎么做的」——那是不合格的。
这一版每个问题都补三件事：**业界做法（带出处）**、**我们采用了什么**、**为什么还没采用剩下的**。

先说结论：下面 10 个问题里，**有 5 个已经被业界解决到可以直接抄的程度**，我们这一轮抄了 3 个；
剩下 5 个是真问题——要么需要模型/服务，要么整个行业也没有可靠答案。

## 这一轮直接采纳的机制

| 机制 | 出处 | 落在哪 |
|---|---|---|
| 写时失效：冲突时关闭旧事实有效期，不删除 | Zep / Graphiti 的双时间模型 | `consolidation._find_conflicts` |
| 删除前检查剩余来源：所有父来源没了才失效 | Zep `remove_episode` | `runtime._has_surviving_parent` |
| 原子领取任务（`UPDATE ... RETURNING`） | 队列系统的标准做法 | `JobRepository.claim` |
| 召回内容标记来源与指令性措辞 | spotlighting / 数据标记思路 | `context._looks_instructional` |
| 可用性衰减：半衰期随重要度变化、带回退下限 | cogmem-agent 的 `half_life = base × (1+arousal)` | `retrieval/decay.py` |

## 1. 提示注入与记忆污染

**业界做法**
- 微软的 **spotlighting**（数据标记）：给不可信内容加定界符、数据标记或编码，
  让模型在结构上区分「资料」和「指令」；
- cogmem-agent 用 `<memory-context>` 标签包住召回内容；
- OWASP LLM Top 10 的建议是输入校验 + 权限隔离 + 人工确认，
  但**没有任何方案给出保证**，因为 LLM 没有类型系统。

**我们采用了**
`<memory-context usage="reference-only">` 围栏 + 声明「不是指令」；
每条记忆标出 `说话者=用户/角色/系统`；正文匹配「忽略之前/从现在起/你必须」等模式时
打上 `⚠含指令性措辞` 标签。

**为什么没做更多**
真正的防线在宿主：记忆内容不能触发工具调用（能力隔离），高危操作要人工确认。
引擎只能做「标记」，做不了「阻止」。这不是偷懒，是职责边界。

**还可以做**
红队测试集（50 条注入式记忆，测注入成功率）；写入时把指令性内容隔离到待确认队列。

## 2. 抽取质量

**业界做法**
- **Mem0** 论文里是 LLM 抽取 + 更新阶段四选一（ADD / UPDATE / DELETE / NOOP），
  候选与 top-10 相似记忆一起交给模型决策（[arXiv 2504.19413](https://arxiv.org/abs/2504.19413)）；
- 但 Mem0 **现行实现改回了单遍 ADD-only**：理由是「用户历史不是一份可覆盖的档案，而是一条时间线」，
  过期交给检索排序和时间元数据，只有应用明确要求时才 update/delete
  （[Mem0: memory eviction and forgetting](https://mem0.ai/blog/memory-eviction-and-forgetting-in-ai-agents)）；
- **Cognee** 用本体（ontology）约束抽取，避免每次跑出来的实体类型都不同；
- **Graphiti** 用微调过的小模型做图构建，比通用大模型更稳、更便宜。

**我们采用了**
规则抽取 + 幂等键 + 认识论标记（`explicit_setting / user_report / observed / inferred`）。
更重要的是采纳了 Mem0 的**现行**结论：只增不改，把「变化」表达成有效期，而不是覆盖。

**为什么没接 LLM**
零依赖是硬约束；且没有评估集时，换模型无法证明变好。这一条要等第 10 条（评估）先做。

## 3. 中文语义检索

**业界做法**
- **Mem0** 的检索是多信号融合：语义向量 + BM25 关键词 + 实体匹配
  （[How Mem0 works](https://docs.mem0.ai/core-concepts/how-it-works)）；
- **cogmem-agent** 用 Ollama + `multilingual-e5-large`，embedding 不可用时 **FailOpen** 退回关键词；
- 主流做法就是「向量找语义、BM25 找精确词」，两者融合，谁也不替代谁。

**我们采用了**
trigram（≥3 字）+ LIKE（2 字）+ 哈希向量的三路候选，RRF 融合——结构上就是 Mem0 那套，
只是把「语义向量」换成了字面哈希占位。

**为什么没换真模型**
需要运行时或 API key。换的时候只需实现 `Embedder` 协议（`name/dim/embed`），
然后 `reindex`；但**阈值必须重新标定**（我们 256→1024 维时就吃过一次亏）。

**真正的差距**
不是「有没有向量」，而是「BM25 只覆盖了 3 字以上」。两字词现在只有 LIKE，
没有词频加权。这是可以自研补上的一块，不需要外部服务。

## 4. 记忆冲突与双时间

**业界做法**
- **Graphiti** 给每条事实四个时间戳：`created_at`（何时学到）、`valid_at`（何时在世界上成立）、
  `invalid_at`（何时不再成立）、`expired_at`（何时得知它失效）
  （[Zep: Stop using RAG for agent memory](https://zep-memory-for-ai.ghost.io/stop-using-rag-for-agent-memory)）；
- 冲突时不删除，只关闭有效期；查询「现在」和「当时」是两个一等操作；
- 冲突检测本身由 LLM 在写入时判定（新事实 vs top-k 相似事实）。

**我们采用了**
`valid_from / valid_to` + `supersedes` 链接 + `retrieve(as_of=...)` 回放。
这一轮补上了**写时冲突消解**：单值谓词（名字/住处/生日…）换值、或同宾语的否定翻转时，
旧事实自动关闭有效期并写新值，历史仍可查。

**为什么只能做到规则级**
「喜不喜欢猫」和「住在哪」的冲突判断难度天差地别，规则只能覆盖单值属性。
LLM 判冲突是正解，但我们没有模型；而且**误判冲突比漏判更危险**（会把正确记忆标成历史），
所以规则故意保守：拿不准就不冲突。

**缺口**
没有 `expired_at`（系统何时得知失效，现在用 `updated_at` 近似）；没有矛盾检测队列。

## 5. 去重的正确性与可逆性

**业界做法**
- Mem0 的结论：不要试图用「UPDATE」覆盖历史，保留时间线，靠检索排序；
- Graphiti：事实是图的边，冲突只关闭有效期，边永远保留，删除是单独的操作；
- 业界普遍不为「合并」提供 undo——他们压根不合并，只做去重（不写入重复项）。

**我们采用了**
Jaccard ≥ 0.85 合并，副本标 `superseded` + `part_of`，主记录继承全部来源事件。
合并是「保守」的：只在同类型内、只合并几乎一样的表述。

**为什么不做 undo**
需要事件溯源（所有写入变成不可变事件，合并只是投影）。这是架构级改造，
不是加个字段能解决的。现在的折中是：合并不删数据，最坏情况是多一条历史。

## 6. 摘要

**业界做法**
- **Zep** 产出三种摘要：episode → thread summary → user summary，每层都挂在来源上；
- **Mem0** 的抽取阶段会维护一份「对话摘要」，异步刷新，只用于给抽取提供上下文，不当事实；
- 共同点：**摘要都是派生物，必须能回到来源**。

**我们采用了**
`summaries` 表只存主题 + 时间跨度 + 一句概述 + 来源 ID；展开必须 `expand_summary()` 回源；
来源变化时卡片标 `stale`。生成方式是抽取式（不写新句子），避免编造。

**缺口**
读起来像清单不像概述；主题词靠二字词频率，遇到指代会失效。
换成生成式摘要是替换 `_compose()` 一个函数，但需要模型。

## 7. 并发与崩溃恢复

**业界做法**
- 队列领取用 `UPDATE ... RETURNING` 或 `SELECT FOR UPDATE SKIP LOCKED`，配合租约与心跳；
- 数据可靠性用「命令日志 + 定期检查点」：celiums-memory 用 Durable Object 命令日志 +
  三代快照，宣称已确认写入 RPO 0；
- 本地优先系统再叠一层同步协议（服务端权威或 CRDT）。

**我们采用了**
这一轮把任务领取改成了单条 `UPDATE ... RETURNING`，两个进程同时取不会重复领取；
写操作全部在事务里；核心与检查点用版本号 CAS。

**缺口**
没有租约（进程崩溃后 running 任务不会自动回收），没有跨设备同步，
没做过「写入过程中 kill -9」的恢复测试。

## 8. 删除的完全性

**业界做法**
- **Zep** 的 `remove_episode` 规则很干净：删一个来源时，一条事实只有在
  **没有任何其它来源支持它**的情况下才删除
  （[How Zep tracks provenance](https://blog.getzep.com/how-zep-tracks-provenance-in-agent-memory)）；
- 学术界对「可证明删除」的答案是 crypto-shredding：每条数据一把密钥，删密钥即不可读；
- 工程上还要处理派生索引、缓存、备份、摘要。

**我们采用了**
这一轮实现了 Zep 的支持检查：删除前查 `derived_from` 的其它父来源，
还有活着的来源就保留派生记忆。加上软删除 + FTS/向量同步清理 + 摘要重建。

**缺口**
备份与已写进摘要正文的内容仍可能残留；没有密钥销毁机制。

## 9. token 计量与预算

**业界做法**
宿主侧用目标模型的 tokenizer 精确计数；上下文按预算做打包（摘要优先、证据按分排）；
Mem0 的做法是「top 5 条、200 token 以内」这种硬上限。

**我们采用了**
保守估算（中文 1 字≈1 token）+ 条数与 token 双上限 + 摘要优先。

**缺口**
没有可插拔 tokenizer。加一个 `TokenCounter` 协议不难，难的是拿不到各模型的计数表；
这个应该由宿主注入，而不是引擎内置。

## 10. 评估

**业界做法**
- **LongMemEval**：多会话推理、知识更新、时间推理、拒绝无依据回答；
- **LoCoMo**：长对话记忆；
- **MemBench** 等新基准；Mem0 与 Zep 都在论文/博客里报这几个集的结果；
- 共同点：都有标注、都有「无依据」负例、都区分能力维度。

**我们采用了**
10 条自造计分用例 + 2 条故意失败的观察项 + 单独的「无依据拒绝」口径。
它只是回归保护，不是质量证明——这一点写在 README 里。

**为什么没接公开基准**
中文陪伴场景和 LongMemEval 的英文个人助理场景差异很大；
直接跑分会得出一个看似权威但与本项目无关的数字。正确做法是**借它的题型**，自建中文集。

---

## 别再当问题研究的三件事

这三件已经有成熟做法，属于「照抄就行」：

1. **任务领取的原子性** —— 已改成 `UPDATE ... RETURNING`；
2. **删除的支持检查** —— 已按 Zep 的规则实现；
3. **冲突时的历史保留** —— 关闭有效期而不是删除，已实现。

## 真正还需要研究的

按依赖顺序：

1. **评估效度**（第 10 条）—— 没有可信度量，后面所有改动都无法判断；
2. **中文检索的两字词排序**（第 3 条的后半）—— 不需要外部服务，BM25 可以自研；
3. **抽取质量**（第 2 条）—— 需要模型 + 评估集，且要先解决「记错比不记更糟」的校验；
4. **冲突检测的语义化**（第 4 条）—— 规则只能覆盖单值属性，剩下要靠模型；
5. **删除的可证明性**（第 8 条）—— crypto-shredding + 备份策略，工程量大但路径清晰。

前两项做完，这个项目才算从「能跑的骨架」变成「有依据的系统」。
